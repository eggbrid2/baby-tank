# AI 动作组、对话延迟、遥控布局与直行补偿记录

日期：2026-10-17

## 结论

- 明确的中文行走祈使句现在由服务端窄语法独立授权；模型可以选择 2-9 秒时长、灯光和回复表情，但不能否决明确指令，也不能凭自己的 JSON 擅自让车移动。
- 普通行走回复采用同一时间线：TTS 播放开始时，同时启动屏幕表情、可选灯光和有界底盘动作。手机遥控或 STOP 会通过控制 epoch 抢占该动作组。
- “去看看前面有什么”仍走视觉探索：机器人按需拍 JPEG，视觉模型决定 `stop/forward/backward/left/right`、灯光和表情，每组最多 3 步/15 秒。连续视频不上传云端；否则延迟、带宽、费用和隐私成本都不可控。
- 视觉探索不能与首段 TTS 同时再开第二条 TLS 视觉连接。摄像头初始化后内部最大连续内存块只有约 7.5 KiB，两个并发 TLS 会有明显内存风险。因此第一版先说“我看看”，再拍照规划；拿到每一步视觉结果后，表情、灯光和运动并行执行。

## AI 控车恢复

原链路要求“明确 ASR 指令”和“模型恰好输出同方向 action”同时成立，模型漏字段就不会动。这是错误的授权耦合。现在：

1. `explicitDriveIntent()` 只接受独立的前进、后退、左转、右转祈使句；否定、假设、引用和讨论仍拒绝。
2. 明确指令即生成安全动作；模型同方向提案只补充时长和灯光，缺失时默认 2000 ms、灯光不变。
3. 服务端返回动作协议 v4；固件在 HTTP 响应头完成时解析，在 PCM 真正开始播放时启动动作任务。
4. 动作任务仍固定 600‰，2-9 秒；BLE/急停/遥控模式改变控制 epoch 后，旧动作无法重新取得底盘控制权。

## 延迟优化

- VAD 句尾静音从 700 ms 缩短到 500 ms。
- 设备 TTS 播放预缓冲从 16,000 样本（1 秒）降到 8,000 样本（0.5 秒）。
- 删除主模型回复缺少逐句情绪时的第二次“情绪标注器”模型请求；缺失时直接使用主回复情绪。
- 多句 TTS 从串行生成改为并行生成，再按原顺序拼接，精确保留 PCM 样本偏移的表情切换点。
- 最近一次旧线上完整对话样本为：ASR 3985 ms、LLM 956 ms、第二情绪模型 627 ms、TTS 1148 ms、首包前总计 6720 ms。这里 ASR 数字包含约 5.8 秒用户音频的流式上传过程，不能误读成“闭嘴后仍等 4 秒”。新版本理论上直接移除其中 627 ms，并减少约 500 ms 播放预缓冲和 200 ms 句尾等待；仍需用更新后的真实对话指标复测，不能把理论节省当成实测。

## 直行偏右

- App 前进映射原本就是左右相同值，问题不在方向按钮。
- 上游 ESP32-C2 底盘是无编码器的开环 PWM，并提供 2.5% 步长的左右电机系数命令，说明厂商设计本身预期个体差异。
- 本机向右偏意味着左履带相对更快。头部固件现在仅在“左右同向且同值”的直行命令上把左侧降到 97.5%；原地转向不受影响。
- 这是固定偏差补偿，不是闭环循迹。电池电压、地面摩擦、履带松紧和载荷变化仍会影响方向；最终产品若要求稳定直线，需要编码器或 IMU 闭环。

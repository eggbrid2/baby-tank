# 运行时资源回收与卡死自恢复

日期：2026-10-23

## 问题前提

- “清缓存”不能直接解决所有卡顿。视频发送阻塞、对话状态机没有推进、堆碎片、
  云端进程失去响应是不同故障，需要分别设置退出边界。
- Android 视频帧没有落盘缓存；离开遥控页后应关闭连接并丢弃位图引用，让 GC
  回收。对仍被 Compose 绘制的位图主动调用 `Bitmap.recycle()` 反而可能触发崩溃，
  因此本次没有采用手工回收位图。
- 看门狗和自动重启只能缩短不可用时间，不能消除根因；反复重启仍需结合设备日志、
  Reset reason 和堆统计定位。

## 已补齐机制

### Android App

- Activity 进入后台、系统报告运行内存偏低、离开遥控页或页面生命周期进入
  `ON_STOP` 时，主动断开视频流、停止运动并退出遥控模式。
- 视频解码队列保持 `CONFLATED`，只保留最新帧；JPEG 使用 RGB565，减少单帧
  Java 堆占用。没有新增磁盘视频缓存。

### 云端服务

- 每 60 秒淘汰过期的登录限制、认领限制、画画限流、视觉会话、绘画会话和已结束
  探索任务；每 6 小时清理数据库中过期会话和已失效认领记录。
- `/healthz` 同时检查 SQLite 是否可查询，数据库异常时返回 503。
- 容器入口每 15 秒探测健康状态，连续 3 次失败后终止 Node 进程并退出，由 Docker
  的 `restart: unless-stopped` 拉起；Compose 为容器设置 512 MiB 内存上限并启用
  init 进程处理孤儿进程和信号。

### 头部固件

- 摄像头 HTTP 发送设置 3 秒 socket 超时，避免客户端断开或网络拥塞时发送任务永久
  卡住。现有“最新帧”队列、编码生产者超时与退出清理继续保留。
- 主循环每 5 秒检查活动对话阶段和 turn 是否推进。连续 180 秒无推进时先停止底盘、
  关闭云端语音连接并重置前台运行时；连续两次恢复 API 失败才重启。
- 内部 SRAM 可用量低于 8 KiB，或最大连续块低于 4 KiB，连续 6 次采样（30 秒）
  后执行一次前台恢复；再持续 30 秒才重启，避免瞬时分配峰值造成重启循环。
- FreeRTOS Task Watchdog 调整为 15 秒并启用 panic。阈值给已观察到约 6 秒的 TLS
  ECDHE 留出余量，同时让真正不让出 CPU 的任务最终由芯片复位。

## 未验证项与风险

- 按要求未做实机验证。180 秒停滞、8 KiB/4 KiB 堆阈值和 15 秒任务看门狗是根据
  当前代码与历史内存记录设置的保护值，不是目标硬件压力测试后的最终参数。
- 启用 Task Watchdog panic 后，真正卡死会从“永久无响应”变成“自动重启”；代价是
  某些超过 15 秒且不喂狗的异常慢路径也可能触发重启。部署后应重点检查
  `rst:...`、`task_wdt`、`internal_free` 和 `internal_largest` 日志。
- 本次没有更改分区表来启用持久化 core dump，避免影响既有 OTA/数据分区兼容。
  因此自动恢复后主要依赖串口/远程日志和 reset reason，而不是完整崩溃转储。
- Docker 的 512 MiB 是故障隔离上限，不是正常内存目标；若触发 OOM，应先确认是
  泄漏、请求峰值还是模型响应过大，再决定调整上限，不能只增加内存掩盖增长趋势。

## 部署边界

- App 生命周期释放需要更新 Android APK。
- 摄像头发送超时、低内存恢复和任务看门狗需要更新头部固件。
- 临时状态清理、健康检查和进程自拉起需要重新构建并部署云端容器。
- 三部分可独立生效，但只有同时更新才能覆盖端到端的资源与卡死路径。
